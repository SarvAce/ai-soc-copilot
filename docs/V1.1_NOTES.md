# What proposal v1.1 has to change

Proposal v1.0.2 (`POC_SPEC.md`, and the submitted `.docx`) was written before the
build. This file lists everything the build changed, learned or measured, section
by section, so v1.1 can be edited from one list.

**The submitted `.docx`, `.pptx`, `POC_SPEC.md`, `PITCH_DECK.md` and
`docs/figures/` are not edited.** This file is the change list for the next
version, not a patch to the submitted ones.

Every entry names the `docs/DEVIATIONS.md` row it comes from. Where a number
appears it is measured, from `results/`, never quoted from memory.

---

## 1 · The headline change: §18.2 becomes results, not targets

v1.0.2 states §18 as a plan — "these are targets, not results", as slide 9 says.
v1.1 reports what was measured. From `results/summary.md`, measured **2026-10-21**
in mock mode, configuration `8943cb7bfe49`, knowledge base `68368958f1c7`, on the
100-case held-out set (seed 42):

| Metric | Target in v1.0.2 | Measured | Verdict |
|---|---|---|---|
| Alert recall | 100% for the in-scope templates | 100.0% (80/80) | met |
| Alert precision | no case for S7 or an N − 1 variant | 100.0% (80/80) | met |
| Disposition accuracy | ≥ 95% | 100.0% (290/290) | met |
| Dangerous misses | 0 | 0 | met |
| Groundedness | 100%, enforced by the gate | 100.0% (1258/1258) | met |
| Critic catch rate | ≥ 95% per mutation type | 100%, lowest of 17 types | met |
| Critic false alarms | 0% | 0.0% (0/10) | met |
| Termination | 100%, no recursion errors | 100.0% (80/80) | met |
| Determinism | 100% over 3 mock-mode runs | 10/10 scenarios stable | met |
| Efficiency | reported, no target | 14.6 queries, 15.9 facts per case, 0.18 s per case | reported |

**§18.5 must keep all three caveats when it reports these.** They are the
difference between an honest result and a circular one:

1. Internal validity on synthetic data: the same team wrote the generator and
   the rules.
2. The held-out labels are inherited from the templates (D10) and the
   randomisation is constrained so a case keeps the answer its template
   promises (D33). The set tests generalisation across randomised instances of
   known patterns, not that the patterns are right.
3. **S9 remains a documented miss.** Low-and-slow spraying is below every window
   threshold and is not in the held-out templates, so it cannot appear in the
   table; `tests/test_detector.py` reproduces it deliberately.

### §18.2 also gains a result v1.0.2 did not anticipate

**In Ollama mode, every local-model draft was rejected and the template was
released.** Measured on S2 and S4 (`results/models_S2_*.json`,
`results/models_S4_*.json`), after the D28 fix:

| Scenario | Model | Draft calls | Drafts rejected | Checks that fired | Released by | Verdict |
|---|---|---|---|---|---|---|
| S2 | mock | 1 | 0 | — | first draft | SUSPECTED_COMPROMISE P2 |
| S2 | qwen3-coder:30b | 2 | 2 | R3 | template | SUSPECTED_COMPROMISE P2 |
| S2 | qwen3.5:4b | 2 | 2 | R3, R7, R10 | template | SUSPECTED_COMPROMISE P2 |
| S4 | mock | 1 | 0 | — | first draft | LIKELY_BENIGN P4 |
| S4 | qwen3-coder:30b | 2 | 2 | R3, R7 | template | LIKELY_BENIGN P4 |
| S4 | qwen3.5:4b | 2 | 2 | R3, R7 | template | LIKELY_BENIGN P4 |

This is the **SOC-PoC-013 rejection rate**, and on these two scenarios it is
100% for both local models. v1.1 should say so plainly, and should draw the two
conclusions the data supports:

- **The design worked.** The verdict and the priority are identical in all six
  runs, because code computes them; the gate caught every ungrounded draft, and
  the fail-safe released a correct report written from the facts. This is
  exactly the behaviour §15.5 and Table 25 specify.
- **A 4B or 30B local model is not yet good enough to pass R3 and R7 on this
  prompt.** R3 (every number, address, time and username must be in the cited
  facts) and R7 (no certainty wording) are what they fail. v1.1 should present
  the local model as *measured and rejected*, not as a working narrative writer,
  and should list prompt tightening, few-shot examples and a larger model as the
  next experiment.

> Consequence for the demonstration: Ollama mode shows the template fallback,
> not a model-written narrative. `docs/DEMO.md` says so.

## 2 · Section by section

### §11.7 (work packages) and Appendix B — WP8

- **D35.** `SqliteSaver` is **dropped added value**. Stage 2 keeps its
  `MemorySaver`, no new dependency is added, and a paused case does not survive
  a restart. WP8 and Appendix B should present it as future work rather than a
  PoC option. The other three WP8 items — the hash-chained audit log with
  `verify_chain`, the §18.3 threshold sweep, and `docs/PEER_TESTING.md` — are
  built.
- **D26.** Appendix B.4 should list `eval/pipeline.py`: a plain-Python driver
  that runs one case through the Table 25 routes, calling the same node
  functions the graph wraps. The evaluation needs a driver with no checkpointer
  in the way.
- **D14.** B.4's single `data/generator.py` is three modules — `data/world.py`
  (population, 14-day history, background noise), `data/scenarios.py` (S1–S11
  and their ground truth) and `data/generator.py` (assembles and writes). One
  module would run past 500 lines.
- **New.** B.4 should also list `soc_copilot/preflight.py`, the
  pre-demonstration check.

### §12 — data, knowledge base and scenarios

- **D13.** Table 19 says `detection_rules.yaml` holds "thresholds, windows,
  hypothesis, ATT&CK IDs", while every threshold must live in `config.yaml`.
  v1.1: the rule file *declares* each rule and names the configuration keys that
  supply its threshold and window; `config.yaml` holds the values.
- **D25.** Table 19's evidence requirements need their scope defined precisely:
  a case-scoped item is answered **once per source address**, and an
  account-scoped item applies only to inventory users. Without this, S11's pivot
  is invisible and bob comes out SUSPECTED_COMPROMISE instead of UNRESOLVED.
- **D19.** Table 19's `geoip.csv` must place S2's and S11's source range
  `203.0.113.32/27` in **NL**, the users' own country, so S2 fires Table 28
  row 4 and not row 2. S1's `203.0.113.7` stays SG. The deck depends on this.
- **D15 and D20.** §12.5 should state the tail of each scenario log explicitly:
  S6a ends five minutes after the last failure (which is its gap), and **S11
  ends with one unrelated sign-in at 18:30**, past the success horizon, so its
  gap is the unchecked pivot and not coverage.
- **D10 and D33.** §12.5 should say where held-out labels come from — the
  template each case was generated from — and that the randomisation is
  **constrained** so a case keeps the answer its template promises. List the
  constraints: the attacker address pool per template, no privileged account in
  a spray template, a burst short enough for R-GUESS to see N failures in one
  window, and every log but S6a's ending past the success horizon.
- **D32.** §12.5 should say the held-out set is built **in memory** and never
  written to disk — 100 written cases would be about 19 MB — and that a case's
  IT tickets travel with the case rather than being written into
  `kb/it_tickets.csv`, so the knowledge-base hash and the design set's
  determinism are untouched.

### §15 — detection and decision

- **D18.** Table 27's R-SPRAY needs one clause added: a sliding window qualifies
  on the **account count** alone, and the median-attempts condition is judged
  over the **merged span** of all qualifying windows. Judging the median per
  window lets a loud multi-account burst through, because a wide burst always
  contains a narrow sub-window that passes.
- **D23 (clarification, not a change).** §15.2's `malicious_indicator` is
  exactly its own three — a threat-intelligence match, persistence, or a new
  country without a travel ticket — and **not** "any MALICIOUS fact". §16.1's
  six MALICIOUS topics answer a different question. v1.1 should make the two
  lists visibly distinct, because reading them as one moves S2 to row 2.
- **D17.** §15 and Table 19 need the **playbook selection rule**, which v1.0.2
  does not give: candidates are the steps of the highest active hypothesis on
  the ladder GUESS < SPRAY < ATO, plus the one step flagged
  `source_containment` when a spray source is in scope; a step whose required
  fact is missing is withheld; and no `contain` step is offered on a
  LIKELY_BENIGN case. An UNRESOLVED case does keep its containment steps. This
  is what reproduces Figure 5's four steps, and check R8 validates against it.
- **D30.** §15.5 should fix the template's opening wording, and note that there
  are **two** routes into template mode: after rejected drafts ("Facts only: the
  local model's drafts did not pass the Report Gate …") and when no model was
  ever asked ("Facts only: no narrative model was asked for a draft …").
  Claiming drafts were rejected when none were written would be untrue.

### §16 — facts, claims and the two gates

- **D21.** §16.5 should read: "a fact mutator exercises the Evidence Gate, and a
  FaultyModel **and a report mutator** exercise the Report Gate". M12, M14, M15
  and M17 change the priority, add a recommendation, add a technique and remove
  the timeline — none of which the narrative schema has a field for, so no
  model could write them. The assembled report is the only place such a fault
  could really arise.
- **D28.** Appendix B.2 should say the **Reporter** fills `Claim.section` from
  the polarity of the fact the claim cites, so the model writes only `text` and
  `fact_ids`. Table 32 should then list **M10 under the report mutator**, beside
  M12, M14, M15 and M17. Measured: before this change R4 was the most common
  rejection for both local models; after it R4 never fires on a model draft.
- **D3 and D27.** Table 31's R3 needs its comparison rules spelled out:
  usernames canonicalised with the §12.2 rule, IP addresses compared with the
  `ipaddress` module, timestamps compared in UTC at hh:mm, numbers compared
  exactly; a token matching an identifier shape (`E00318`, `F05`, `QRY07`,
  `T1110.003`, `P2`, `PB-ATO-01`) is a name, so its digits are not a
  measurement; and any bare word that canonicalises to an inventory account is
  treated as a username. Without the first, R3 rejects its own case file for
  citing `F05`; without the second it misses "the same happened to dave".
- **D29.** Table 31's R2 should allow a draft to cite a fact by its **label**
  (`F05`), which the Reporter maps to the `fact_id` before the gate sees it. A
  label matching no fact is left as written and R2 rejects it.
- **D22.** Appendix B.2's `Fact` carries its topic in `params["topic"]`, so the
  topic is part of the identity hash and two findings from one query cannot
  collide. §16.1's polarity table needs a `mfa_device_registered` row beside
  `persistence`, because §16.1 names both forms of persistence and check R9
  admits T1098.005 only on a device-registration fact.
- **D24.** Table 30 needs two clauses: a negative fact that E5 cannot support is
  **invalidated for sufficiency**, so Table 28 row 1 fires; and E6 still counts
  that item as **attempted**, so it raises no MISSING_CHECK and the case does
  not re-plan. Without the first, S6a is ATTACK_ATTEMPT_NO_ACCESS P3 instead of
  UNRESOLVED P2; without the second, S6a re-plans although Table 20 says no
  retry.
- **D1 and D2.** Appendix B.2 should separate the two jobs an identifier does:
  `fact_id` stays the stable hash and is the merge key, and each fact also
  carries a **label** (`F01`, `F02`, …) assigned per case in order of first
  appearance, which is what the interface and the narrative show. Query IDs work
  the same way. A hash cannot also be the two-digit ordinal Figure 5 cites.

### §17 and Table 33 — the interface

- **D9 and D36.** Table 33 should place the three controls — pick a scenario,
  choose the model, switch fault injection on — in the **sidebar**, where
  Figure 5 draws them, rather than on the Alert queue page; one set then serves
  every page.
- **D31 and D36.** Table 33 should list the **Architecture** page: Figure 2
  beside the compiled `StateGraph` for the selected case, with the nodes that
  ran highlighted, the loops taken marked and the §14.5 counters. It carries a
  run control of its own, because Appendix E.1 reaches it before the
  Investigation trace has run anything.
- **D31.** §17 should say the Investigation trace shows the **whole chain** of
  node executions as Figure 4 draws it, rebuilt from the checkpoints — the final
  state keeps only the last value of every channel, so the first pass's plan,
  the rejected drafts and each gate report would otherwise be invisible.
- **New (gap).** Table 33 gives the Alert queue "upload a JSONL file". The build
  selects from the generated scenarios only; `core/normaliser.normalise_file`
  already does the work, so this is an interface gap. v1.1 should either add the
  uploader or drop the clause. Recorded in `results/traceability.md`.
- **New.** §17 should mention `.streamlit/config.toml`, which turns Streamlit's
  usage reporting off so E.1's "run the demonstration with the network off" is
  literally true.

### §18.3 — the threshold sweep

- **D34.** §18.3 should say the sweep runs over the **held-out set**, not the
  design set, which holds only two logs that should open no case. It reports two
  pairs of counts — over all 100 cases, and over the six templates R-GUESS
  actually decides — because a spray fires R-SPRAY at any threshold. Only
  `detection.guess_min_failures` moves and only Stage 1 is rerun. Measured: the
  default of 5 is the lowest threshold that raises no false alert and still
  detects 53 of 53 R-GUESS attacks. v1.1 must also keep the caveat that the
  N − 1 variants carry exactly four failures by construction, so the left of the
  curve is partly built into the dataset.

### §19 — scope control

- **D11.** The drop order changes: **Ollama mode is required**, so the order
  becomes hash chain, S11, threshold-sweep chart, `SqliteSaver`, live interrupt.
  In the event, the first three were all built and only `SqliteSaver` was
  dropped (D35).

### §20 — risks

- **D12 and D16.** The Ollama risk row should be rewritten around three measured
  facts:
  - **`think=False` is required for correctness, not speed.** qwen3.5 reasons
    before answering by default, and when it does `message.content` is empty and
    the whole reply lands in `message.thinking`, so Pydantic validation fails
    and every draft counts as a failed draft.
  - **Cold start is the real risk.** Measured with `think=False` on the same
    four-fact prompt: qwen3.5:4b 30.6 s cold and 5.4 s warm; qwen3-coder:30b
    52.2 s cold and 16.0 s warm. The application warms the model on selection at
    `keep_alive: 30m`.
  - **The model is named.** `model.ollama_model` is **qwen3.5:4b**, with
    `qwen3-coder:30b` selectable; v1.0.2 names no model.

### Appendix B.6 and Table 39 — the prototype's files

- **D5.** Five files that Table 39 does not list were deleted: `sample_logs/`,
  `infrastructure/`, `docs/screenshots/`, `backend/.env` and `backend/soc.db`.
  `git log --diff-filter=A` shows no add-commit for any of them — they were
  git-ignored or empty directories — so **git history and the `prototype-v0` tag
  do not preserve them.** v1.1 should say so rather than implying Table 39 is
  exhaustive. Nothing the PoC needs is lost.
- **D6.** `requirements.txt` lives at the repository root, since `backend/` is
  removed.
- **D7.** Table 24 should record the versions actually used: pandas 3.0.6 on
  Python 3.14.5, with explicit dtypes on the event columns and no chained
  assignment, against pandas 3.0's new string dtype and copy-on-write defaults.

### Figures and the deck

- **D37.** Figure 5 draws the S2 case file as **case C-02** citing event
  **E00318** over a 02:10–02:38 window; the build opens **C-01** and cites
  **E00570**, at the same 02:41 UTC from the same address, over 02:10–02:35.
  Event IDs are assigned in file order by the seeded generator and case numbers
  by detection order, so neither can be chosen to match a figure without
  changing an ID. Everything Figure 5 asserts about the *case* is reproduced:
  Q1's 24 failures against 12 accounts, Q2's 02:41 success, Q6's 12 targeted and
  4 non-existent names, row 4, P2, two passes with one re-plan, and the four
  steps PB-ATO-01 to PB-ATO-03 and PB-SPR-01. v1.1 should either redraw the
  figure with the generated values or keep the illustrative banner and say so in
  the caption.
- **Slide 6.** The count of **10 of 17** node executions includes
  `analyst_review` and `finalize`, so it is only reached **after** the analyst
  approves; before approval the application honestly shows 8. v1.1 should label
  the figure "10 once the analyst approves", or show 8 at the point the slide
  depicts.

## 3 · What did not change

No ID, threshold, window, rule row, check or expected outcome was changed
anywhere in this build. Every scenario reproduces its Table 20 outcome, the
seventeen checks are the seventeen the spec names, and the bound is 17 completed
node executions. Where the spec was silent, `docs/DEVIATIONS.md` records what
was chosen and why — thirty-seven entries, every one of them reasoned from the
spec rather than from convenience.
