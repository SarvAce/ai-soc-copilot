# Deviations and clarifications

Where `docs/POC_SPEC.md` (proposal v1.0.2) is silent or ambiguous, this file records
what the implementation does, why, and which section it concerns. It feeds proposal v1.1.

No ID, threshold, window, rule row, check or expected outcome has been changed.

| # | Spec section | What the spec says | What the build does | Why |
|---|---|---|---|---|
| D1 | B.2 (`Fact.fact_id`) | "stable hash of kind + params, shown as F07", but Figure 5 cites `F01`, `F02`, `F05`, `F09` | `fact_id` stays the stable hash and is both the merge key and what claims cite. Each `Fact` also carries a `label` (`F01`, `F02`, …) assigned per case in order of first appearance; only labels are shown in the UI and the narrative. | A hash cannot also be a two-digit ordinal. Keeping the hash as the merge key is what makes a second pass merge facts instead of duplicating them (B.1). Labels are assigned deterministically, so the mock-mode report hash stays identical across runs (§18.2 determinism). Approved 20 Oct 2026. |
| D2 | §5 (query IDs) | Query IDs start with `QRY` | Same scheme as D1: a stable query identity, plus a per-case display label `QRY01`, `QRY02`, … in execution order. | Consistency with D1 and with Figure 5, which shows `QRY07`, `QRY10`–`QRY12`. Approved 20 Oct 2026. |
| D3 | Table 31, check R3 | "Every IP, number, timestamp and username in the claims and summary appears in the cited facts" | Before comparing, usernames are canonicalised with the normaliser's own function (§12.2 rule 2) and IP addresses with the `ipaddress` module (§12.2 rule 3); timestamps are compared in UTC at hh:mm precision; numbers are compared exactly. A username must still appear in the cited facts **and** be an inventory user. | A local model writes `Alice@corp.example` where the fact says `alice@corp.example`, and `2001:db8::1` for `2001:0db8:0000::1`. Rejecting those would measure spelling, not groundedness, while a genuinely new username or address still fails. Approved 20 Oct 2026. |
| D4 | Table 20, S11 | "Retry cap set to 1" against the Table 38 default of 2 | S11 carries its own evidence-retry cap of 1 in its scenario definition; `config.yaml` keeps the default of 2, and the termination tests use the default caps. | Reads as a per-scenario override to force the exhaustion path, not a change to the default. Approved 20 Oct 2026. |
| D5 | Table 39 | Lists the prototype's files but not `sample_logs/`, `infrastructure/`, `docs/screenshots/`, `backend/soc.db`, `backend/.env` or `.idea/` | All deleted except `.idea/` (IDE settings, git-ignored). The commit before the deletion is tagged `prototype-v0`. | The PoC uses only generated synthetic data (§12), so the prototype's free-text keyword-era logs and its empty directories have no role. Git history and the tag keep everything. Approved 20 Oct 2026. |
| D6 | Table 39 | "`backend/requirements.txt` rewritten in UTF-8 with pinned versions" | `requirements.txt` lives at the repository root, since `backend/` is removed. | The `CLAUDE.md` run commands expect it there. Approved 20 Oct 2026. |
| D7 | Table 24 | "pandas DataFrame" | pandas 3.0.6 on Python 3.14.5, with explicit dtypes on the event columns and no chained assignment. | Only Python 3.14 is installed on the build machine, and 3.0.x is the earliest pandas with 3.14 wheels. Explicit dtypes guard against pandas 3.0's new string and copy-on-write defaults. The Python version is not to change without asking. Approved 20 Oct 2026. |
| D8 | Table 19, playbooks | "adapted from the prototype" | `kb/playbooks.yaml` keeps the prototype's four `BRUTE_FORCE` actions as `PB-SPR-01`, `PB-SPR-02`, `PB-SPR-03` and `PB-GUESS-02`, each with a step ID, a type and an approval flag. Its `PORT_SCAN`, `MALWARE`, `RANSOMWARE` and `SQL_INJECTION` playbooks are dropped. | The PoC covers identity attacks only (§9), so a ransomware playbook has no hypothesis to attach to. |
| D9 | §17 | Five Streamlit pages | One `app.py` with a sidebar radio and page bodies in `soc_copilot/ui/`, rather than Streamlit's multipage `pages/` folder. | Matches the left-hand navigation in `fig5_wireframe.png` exactly and keeps a single `st.cache_resource` graph and checkpointer. |
| D10 | §12.5 held-out set | 100 cases "from the S1–S6, S8 and S10 templates" | Each held-out case inherits its ground-truth label from the template it was generated from; N − 1 variants are labelled "no alert expected", as S7 is. | §12.5 states the construction but not where the labels come from; the template is the only available source. |
| D11 | §19 scope control | Drop order: Ollama mode, hash chain, S11, threshold-sweep chart, SqliteSaver, live interrupt | Ollama mode is **required** in this build. The drop order becomes: hash chain, S11, threshold-sweep chart, SqliteSaver, live interrupt. | Instructed by the team on 20 Oct 2026: Ollama mode is to be demonstrated, so it is no longer the first thing dropped. |
| D12 | §20 (Ollama risk) | "The mock model is the default; Ollama is added value only" | Mock stays the default. When Ollama mode is selected the app warms the model with one tiny call at `keep_alive: 30m` behind a spinner and shows cold/ready status in the sidebar. A timeout falls back through the redraft and then the template, by the existing Table 25 routing. | Measured on this laptop: `qwen3-coder:30b` takes 127 s on the first call after a reboot and 5.8 s warm. Without warming, the first demo case looks hung. Approved 20 Oct 2026. |
| D13 | Table 19 vs CLAUDE.md rule 8 | Table 19 says `detection_rules.yaml` holds "thresholds, windows, hypothesis, ATT&CK IDs", while CLAUDE.md requires every threshold to live in `config.yaml` | `detection_rules.yaml` declares each rule — its hypothesis, ATT&CK ID, grouping and *which* configuration keys supply its threshold and window — and `config.yaml` holds the values. | Keeps one source of truth for every number while leaving the rule definitions in the knowledge base, where the Detector reads them. Changing a threshold still means editing one file. |
| D14 | B.4 (`data/generator.py`) | One generator module | Three: `data/world.py` (population, 14-day history, background noise), `data/scenarios.py` (S1–S11 and their ground truth) and `data/generator.py` (assembles and writes the files). | One module would run past 500 lines, against the CLAUDE.md limit of about 300 with one test file per module. The split is by subject, so each file can be explained on its own. |
| D15 | §12.5, S6a | "the log ends 5 minutes later" | S6a's file ends with one unrelated sign-in at 12:10, five minutes after the last failure at 12:05, and nothing after it. | Coverage is the file's last accepted timestamp (§12.2 rule 7). Without that trailing record the log would end at 12:05, making the covered window 5 minutes rather than the 10 the scenario describes. |
| D16 | Appendix B.3, Table 38 | "OllamaModel ... options={"temperature": 0, "seed": 7}"; the model is not named in the spec | `model.ollama_model` is **qwen3.5:4b**, with `qwen3-coder:30b` still selectable from the sidebar dropdown (filled from `ollama.list()`). Every `ollama.chat` call passes `think=False` alongside the Table 38 options. | qwen3.5 reasons before answering by default, and when it does, **`message.content` comes back empty** — the whole reply lands in `message.thinking`, so the Pydantic validation of `NarrativeDraft` fails and every draft counts as a failed draft. `think=False` is therefore required for correctness, not just for speed. Measured warm, on the same four-fact prompt: qwen3.5:4b 5.4 s, qwen3-coder:30b 16.0 s; both returned schema-valid JSON citing all four fact IDs, and both were byte-identical across two runs. Instructed by the team on 20 Oct 2026. |
